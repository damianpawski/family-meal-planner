# Architecture: family meal planner

Draft 3 · 2026-11-10 (review fixes from [architecture-review.md](architecture-review.md) and two reviews on 2026-11-10; proxy trust and milestone names updated 2026-11-15 from [milestones-review.md](milestones-review.md)) · how [spec.md](spec.md) gets built. The spec says *what* must be true; this file says *how*. When the two disagree, the spec wins and this file changes. The sync protocol's details live in [sync-contract.md](sync-contract.md), which wins over this file on those details.

Each decision marked **ADR** gets its own record in [docs/adr/](../docs/adr/README.md) when the milestone that first depends on it starts.

## 1. Shape of the system

```
Phone / desktop browser                         VM (Docker Compose)
┌──────────────────────────────┐              ┌───────────────────────────────┐
│ Blazor WASM app (PWA)        │   HTTPS      │ Caddy (TLS, Let's Encrypt)    │
│  ├ UI components (RCL)       │ ───────────▶ │ ASP.NET Core host             │
│  ├ Local store (IndexedDB)   │  same origin │  ├ serves WASM files          │
│  ├ Outbox (shopping only)    │  cookie auth │  ├ API: vertical slices       │
│  └ Service worker (app cache)│              │  └ Identity, sync endpoints   │
└──────────────────────────────┘              │ PostgreSQL · Seq · photos vol │
                                              └───────────────────────────────┘
Local dev: Aspire AppHost runs the same pieces + Mailpit, with the Aspire dashboard.
```

- **One origin.** The ASP.NET Core app hosts both the WASM files and the API, so there's no CORS and cookies stay first-party. **ADR**
- **Components in a Razor Class Library**, so a MAUI Blazor Hybrid shell can reuse them later.
- **Vertical slices** on the server: `Features/<Area>/<UseCase>/` holds the endpoint, request, handler, validator and its tests. Shared domain types live in `Domain/`. EF Core is used only on the server.
- **Proxies:** the app runs behind a proxy everywhere it's reachable from a phone (the tunnel locally, Caddy in production), so it reads `X-Forwarded-For`, `-Proto` and `-Host` only from the proxies named in a setting. The setting defaults to loopback, which fits the tunnel; in production it names the Compose network, because Caddy runs in its own container and doesn't reach the app from loopback. Without that, every request looks like plain HTTP from one address, which breaks HTTPS redirection and per-address rate limiting.

## 2. Data and identity

- **Ids:** UUID v7. Time-ordered ids keep Postgres indexes healthy. The client generates the id for shopping extras and for every record a change batch creates (a planned dish, an ingredient line, a step), so a retried batch is recognised instead of creating a duplicate ([sync contract §4](sync-contract.md#4-retries-and-lost-responses)). The server generates all other ids. The primary key is `id` alone. A client id that already exists, in this family or another, is refused by the primary key itself and turned into a refusal (SYNC-55, DOM-10), never by checking first and inserting after, which would race.
- **Family isolation, in two layers (DOM-10, SEC-06):**
  - **Reads:** every family-owned table has `family_id`, and an EF Core global query filter applies it. The family comes from a **database lookup on every request** (person → family), not from a claim in the cookie, so a removed person loses access on their next request rather than when Identity next checks the security stamp (every 30 minutes by default). Code that runs with no signed-in person (background jobs, `mealplanner` commands) must set the family explicitly; with no family set, the filter **throws**, so it can never fall back to "no filter".
  - **Links, enforced by the database:** besides the primary key, every family table has a unique key `(family_id, id)`, and every foreign key between family tables uses it (for example `planned_dish (family_id, dish_id) → dish (family_id, id)`). Postgres then refuses a row that links to another family's record, whatever the code does, including raw SQL such as the grocery upsert, which bypasses query filters.
  - Integration tests prove that a cross-family read, write and link all fail, through every write path: API handlers, background jobs, `mealplanner` commands and raw SQL. **ADR**
- **Database names are snake_case** (the author, 2026-10-14): `planned_dish`, `family_id`, `deleted_at`, so tables and columns can be queried in DBeaver or psql without double quotes (`SELECT name FROM dish WHERE family_id = …`). EF Core keeps PascalCase in C# and maps it with **EFCore.NamingConventions** (Apache-2.0, by the Npgsql maintainer): `options.UseNpgsql(…, o => o.MigrationsHistoryTable("__ef_migrations_history")).UseSnakeCaseNamingConvention()`. It's on from the very first migration, because renaming later means a migration that touches every table. Index, key and constraint names follow the same convention. EF Core stays on 10.x until this package supports 11 (details in ADR 13). **ADR**
- **Dates and times (DOM-24):** slot dates are `date` (no time). The family's IANA time zone is stored on `family`, and "today" is computed from it on both client and server. Instants are `timestamptz` in UTC. **All code reads the clock through .NET's `TimeProvider`** (injected on the server, and in the WASM app for "today"), never `DateTime.Now` or `DateTime.UtcNow`; an analyzer rule (banned API list) fails the build if they appear. Tests use `FakeTimeProvider` to jump to 18:59 on a Sunday, cross midnight in Warsaw while the phone is in London, or move 30 days ahead (DOM-24, NOTE-03, NOTE-09, RATE-02, SYNC-50). Playwright tests set the browser clock with `page.Clock`.
- **Groceries (DOM-12, DOM-13):** `grocery` has a unique index on `(family_id, normalized_name)` (trimmed, single-spaced, lower-cased). Creating a grocery is an upsert (`INSERT … ON CONFLICT DO NOTHING`, then select), so two people adding "Sour cream" at once get the same row. (Because every write takes the family lock first, two upserts for one family can't actually race; the DOM-13 test therefore also runs the upsert without the lock, so it tests the upsert itself.) Ingredient lines and shopping items hold a `grocery_id`. The shopping list combines lines by `grocery_id`, not by text. `grocery.unit_kind` (weight, volume, or one count unit) is set on first use; ingredient and item units are validated against it on the server, so amounts are stored in a base unit (g, ml, or the count) and always add up (DOM-08).
- **Concurrency on online edits (SYNC-20):** the record's change counter (below) is its EF concurrency token; it changes on every write, so no separate `version` column is needed (the author, 2026-11-10). A save sends the counter the person last saw, and a mismatch returns `409` with the current record. Because list items are separate records (spec 0.2), concurrent adds don't collide (SYNC-21). Every record also has `updated_by`, so the `409` can say who changed it ("Maria changed this a moment ago").
- **Change feed (SYNC-30, SYNC-32, SYNC-33):** every write transaction **starts** by locking the family row (`SELECT … FOR UPDATE`), then bumps the family's change counter and stamps every row it writes with that value. Taking the family lock first, always, means two transactions can never wait for each other's locks in opposite orders. The lock makes counters commit in order, which is what prevents the missed-change bug: without it, change 41 can commit after 42, and a device that already pulled 42 never sees 41. Background jobs that change family data (the orphan-grocery cleanup, the tombstone purge) take the same lock and bump the counter like any other write.
  - **Deletions:** every table a phone keeps (SYNC-04) deletes through one generic `tombstone (family_id, entity, id, counter)` table, so a removed ingredient, a merged-away or orphaned grocery, a deleted template or a removed person disappears from every phone, not only shopping lines, extras and planned dishes. Tombstones are purged after 90 days; the family keeps `purged_through`, the highest counter purged, and a device whose cursor is below it does a full re-download ([sync contract §6](sync-contract.md#6-tombstones-and-old-cursors)).
  - **Deleted dishes that were ever planned are never purged**: the row stays with `deleted_at` set, keeping only its name; its ingredients, steps and photo are deleted (with tombstones), and it's hidden from the recipe box and from planning, so today's and past slots keep its name and ratings forever (REC-33). A dish that was never planned is deleted completely, so dishes nobody ever used don't pile up as hidden rows. Dish names are unique only among live dishes: a partial unique index on `(family_id, normalized_name) WHERE deleted_at IS NULL`, using the same normalized name as groceries, so "taco night " is caught as a duplicate and a deleted dish's name is free for a new dish. **ADR**

## 3. Client storage and sync

The exact protocol (requests, results, cursor, paging, retries, idempotency) and its worked examples are in [sync-contract.md](sync-contract.md), finished at the start of M2a.

- **Local store:** IndexedDB through a small JS-interop wrapper (one object store per entity, plus `outbox` and `meta`). SQLite-in-WASM was rejected for v1 because it adds several MB to the first load on the Galaxy A5. **ADR**
- **Reads** always come from the local store. What a screen shows is **the server's state with the outbox replayed on top**, so a pull that lands while ticks are waiting never wipes them off the screen. A **pull** (`GET /api/sync?since={cursor}`, paged, includes tombstones) refreshes the server state on app open, on reconnect, every 20 s while visible and online (so a change shows within SYNC-30's 30 seconds even when the request itself takes a few), and on pull-to-refresh. A pulled record replaces the local one only if its change counter is higher, so a pull that started before an online save can't revert it.
- **Online edits** call the API directly and update the local store from the response. With no connection, the edit controls are disabled (SYNC-03).
- **Edits to lists are sent as separate changes, never as the whole list (PLAN-19, SYNC-21).** A slot sheet collects what the person did and, on Save, sends one small batch: `POST /api/slots/{date}/{meal}/changes` with items like `add { plannedDishId, dishId, servings, position }` (the client makes `plannedDishId`, see §2), `remove { plannedDishId, counter }`, `setServings { plannedDishId, servings, counter }`, `move { plannedDishId, position }`, `skip` / `unskip`, where `counter` is the record's change counter as the phone last saw it. Each item touches one planned-dish record, so Maria adding Rice and Diego adding Salad both survive. The batch runs in one transaction: if any item hits a stale counter, the whole batch is refused with `409` and the current slot (SYNC-20). The same pattern applies to a dish's ingredients and steps in edit mode (REC-30). The LIM-03 limit (8 per slot) and DOM-11 (no duplicate dish) are checked against the slot as it is in the database, not as the phone saw it.
- **Shopping changes go through the outbox** as operations, stored as plain JSON, always, online or offline (the author, 2026-11-10), so ticks and extras follow one set of rules (SYNC-15) instead of mixing versioned edits and operations; online, the outbox is simply sent at once. M2a builds the outbox and its sending online; M3a makes it work offline. Every operation carries `v` (the operation format version, so UPD-03 has something to convert from), `opId` (UUID v7), `personId` (who made it, SYNC-52) and `madeAt` (the phone's time, corrected by its measured difference from the server's clock, [sync contract §5](sync-contract.md#5-ticks-and-extras)):
  - `tick` / `untick`: `{ …, type, itemId | extraId, amountSeen }`. `amountSeen` lets the server split a tick when the line grew meanwhile (spec DOM-22). A tick can point at an extra (`extraId`) instead of a line, because an extra added offline shows as its own line on the phone but may merge into a recipe line on the server (DOM-23); the server then ticks the extra's amount within that line, as a DOM-22 split.
  - `addExtra`: `{ …, type, extraId, listId, groceryName, amount?, unit?, aisle? }`. `extraId` is a client-made UUID v7 for the extra's own source row. The server matches `groceryName` to a grocery or creates one (DOM-16), checks the unit against its unit kind (DOM-08), and merges the extra into an unticked line or gives it its own line (DOM-23). An amount in a unit that doesn't fit the grocery is left off: the extra is kept without an amount, with a note to the person (spec example X14).
  - `removeExtra`: `{ …, type, extraId }`. It points at the extra itself, not at the line, so removing an extra that merged into "350 g Butter" takes away just its 200 g.
  - Until it syncs, an offline extra shows as its own line on that phone (SYNC-16). The live list (DOM-19 to DOM-21) is recomputed on the server from `item_source` rows whenever a planned dish, its servings or its recipe changes, for lists whose last day is today or later only, so editing a recipe never rewrites a list from March or holds the family lock while doing it: unticked lines are **updated in place**, ticked lines are left alone, and any shortfall becomes a new unticked line. **An unticked line keeps its id** for each (list, grocery) pair, so a tick that's waiting on a phone still finds its line after a servings change. `POST /api/sync/shopping` takes a batch and returns a result per operation ([sync contract §4](sync-contract.md#4-retries-and-lost-responses)). The server keeps processed `opId`s to stay idempotent (SYNC-14), resolves ticks by latest `madeAt` (SYNC-15) and clamps future times to server time, and drops ticks for deleted items (SYNC-17).
- **Sending the outbox when the app is closed (SYNC-13):** the outbox lives in IndexedDB as plain JSON operations, ready to POST as they are. Two senders use the same format:
  - the Blazor app, while it's open (on open, on reconnect, on pull-to-refresh);
  - a small JavaScript sender in the service worker (about 30 lines, `sw-outbox.js`), woken by the **Background Sync API** on Android Chrome when the connection returns after the app was closed. It sends only the signed-in person's operations, posts them to `POST /api/sync/shopping` with the session cookie, and deletes the ones the server confirmed. It tells an open app what it sent through a `BroadcastChannel`, so waiting dots don't go stale. The service worker can't run .NET, which is why the operations must need no C# to send. On iOS there is no Background Sync, so the outbox is sent on the next open. This sender is best effort and is built in M3a, after foreground sync is proven.
- **One sender at a time:** both senders take the same Web Lock (`navigator.locks.request('outbox')`) before sending, so two open tabs or a tab and the service worker never send at once. If they ever did, SYNC-14 (duplicates have no effect) keeps it harmless.
- **Persistent storage:** `navigator.storage.persist()` on first sign-in. The photo cache has a fixed budget and evicts the least recently viewed photos first.
- **Pull-to-refresh** is a custom gesture with `overscroll-behavior-y: contain` on the scroll container, so the browser never reloads the page.

## 4. Auth

- **ASP.NET Core Identity:** password hashing, lockout, email confirmation, reset codes.
- **Cookie auth, same origin:** HttpOnly, Secure, **SameSite=Lax**, 30-day sliding expiry (SYNC-50), and antiforgery tokens on every unsafe method (POST, PUT, PATCH, DELETE). Lax rather than Strict so a signed-in person who taps a link in an email ("confirm your new email") isn't shown as signed out; Lax still withholds the cookie from cross-site POSTs and fetches, and antiforgery is the second lock against CSRF. GET endpoints never change data. No JWTs in browser storage. `POST /api/sync/shopping` is the one exception to antiforgery tokens, because the service-worker sender can't get a fresh token. Instead it accepts only `application/json` with a custom header (`X-MealPlanner-Sync: 1`): a cross-site form can't send either, and a cross-site script can't add the header without a CORS preflight, which this origin never allows. It also refuses any operation whose `personId` isn't the signed-in person. **ADR**
- **Invite only:** registration endpoints require a valid, unused, unexpired invite token for that email address (ACC-20 to ACC-23). There is no open sign-up endpoint.
- **Creating a family (ACC-10 to ACC-12):** an admin CLI in the same image: `mealplanner create-family --name <name> --owner <email> --time-zone <IANA zone>`, plus `seed-demo`. It talks to the database directly and sends the owner invite through `IEmailSender`. No HTTP endpoint exists for it, so it can't be reached from the internet.
  - **First deployment:** `deploy.sh` runs `mealplanner create-family` once, reading `FIRST_FAMILY_NAME`, `FIRST_FAMILY_OWNER_EMAIL` and `FIRST_FAMILY_TIME_ZONE` from the VM's env file. The command is idempotent: if any family exists, it logs "Family already set up" and exits successfully, so every later deploy can run it safely.
  - **Future improvement:** any further family still needs SSH access and a manual `docker compose exec app mealplanner create-family …`. That's fine for one family, but should become a proper admin flow (for example a separate admin sign-in with its own page) if the app ever hosts more families.
- **Owner-only actions (ACC-02, ACC-04):** an `OwnerOnly` authorization policy, checked against the family's owner in the database on every request (not a claim cached in the cookie, so a hand-over takes effect at once). Applied to invite, cancel invite, remove person, hand over, delete family and change week start day, with an integration test per endpoint proving a non-owner gets `403`.
- **Rate limiting** on sign-in, code and reset endpoints, plus a batch-size limit on sync. It keys on the real client address, which the forwarded headers (§1) provide.
- **Input safety (spec 8.1):** validation built into .NET 11 (`AddValidation()` for Minimal APIs: DataAnnotations attributes on each request record, checked automatically before the handler runs), with `IValidatableObject` for rules that span fields, and limit constants shared with the client so both check the same numbers. No third-party validation library. Request models per endpoint, never EF entities, so extra fields can't be bound (SEC-06). Kestrel `MaxRequestBodySize` per endpoint (SEC-02). EF Core LINQ and `FromSql` interpolation only (EF turns each interpolated value into a parameter), with a banned-API rule that forbids `FromSqlRaw`, `ExecuteSqlRaw` and `SqlQueryRaw` outright (SEC-04). A banned-API list can't tell concatenation from a constant, so the ban is total; a rare justified use needs an explicit, reviewed suppression. Razor's default encoding, no `MarkupString` with user data, and a strict CSP sent by the app itself, from one security-headers middleware (SEC-05). The same middleware sends the other security headers (HSTS outside Development, `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors 'none'`). Keeping them in the app rather than in Caddy means local dev, the tunnel, tests and production all send identical headers, so SEC-05 is tested from M0. Caddy only terminates TLS and proxies, and adds no headers of its own. ProblemDetails without exception details outside Development (SEC-09). Photos decoded and re-encoded with NetVips (MIT, on libvips, which also reads HEIC) (SEC-08); libvips's native binaries (`NetVips.Native`) are LGPL-3.0-or-later, so how they fit the licence policy, or which library replaces them, is decided in M4a, when the server's image is first built ([ADR 12](../docs/adr/0012-licence-and-supply-chain.md)). ImageSharp was avoided because of its Six Labors licence.

## 5. Other infrastructure

- **Email:** `IEmailSender`, with Gmail SMTP through MailKit (app password) in production and Mailpit locally and in tests.
- **Push notifications (chapter 7):** Web Push with VAPID keys, one subscription row per phone, deleted when the push service answers 404/410. Signing out unsubscribes the phone from push locally first, which works offline, so a wiped phone stops receiving family notifications even if the server never hears about the sign-out; the 404/410 clean-up then removes the row. A hosted background service sends reminders and "Cook tonight" on the family time zone, and flushes 10-minute batches outside quiet hours. There are no cook-mode timers in v1 (spec 6.3): a PWA can't schedule an alert while it's in the background.
- **Background jobs survive restarts:** one hosted service (`BackgroundService` with a `PeriodicTimer`, every minute) runs reminders (NOTE-03), Cook tonight (NOTE-07), the 10-minute batches and quiet hours (NOTE-08, NOTE-09), the orphan-grocery cleanup (REC-19a, daily) and the tombstone purge (90 days). Nothing is scheduled in memory. Each run asks the database what is due, sends it, and records it in a `sent_notification` row with a unique key (person, kind, due date), so a deploy at 18:59 neither skips nor doubles the 19:00 reminder: the next run after the restart still finds it due, and the unique key refuses a second send. Batches are rows in a `pending_notification` table, not in memory. If more than one copy of the app ever runs, each job takes a Postgres advisory lock first, so only one copy works at a time. Jobs work one family at a time, with that family set explicitly (§2).
- **App updates (chapter 7):** the service worker waits instead of skipping waiting; the page shows the update bar and activates the new worker only on Refresh or the next cold start. API endpoints carry a version. Before v1, the server accepts waiting outbox operations from every earlier version and answers any other old request with `426 Upgrade Required`; from v1 on, it keeps **every sync contract version released in the last 30 days** (UPD-04, [sync contract §7](sync-contract.md#7-versions-and-sessions)).
- **Photos:** resized on upload (thumbnail plus full size, WebP) and stored on a Docker volume behind an `IPhotoStore` interface, so S3-compatible storage can be swapped in.
- **Observability:** OpenTelemetry traces and metrics, logs through `ILogger` and the OpenTelemetry exporter (no Serilog, spec decision log 2026-11-10), all sent to Seq in production (30 days of history, alerts) and to the Aspire dashboard locally. Seq runs under its free single-user licence, which fits while the admin is the only one reading the logs. The app only speaks OTLP, so moving to the Aspire dashboard (MIT, in memory only) or a Grafana stack later is a configuration change, not a code change.
- **Database changes vs old phones (UPD-04):** **before v1** (M4b to M13), with four users who update within a day or two, only the outbox format is frozen: migrations may change the schema in one step, and an old phone is asked to update (UPD-05). Contract tests prove that saved outbox batches from every earlier release still apply. **From v1 on,** migrations are **expand, then contract**. A release only adds: new tables, new nullable columns or columns with defaults, and new endpoints or sync fields next to the old ones. Old columns and fields stay readable and written until no supported phone uses them. They're dropped in a later release, at least 30 days after the one that stopped needing them. Renames are done as add new, copy, then drop old. Every sync contract version from the last 30 days is covered by contract tests (saved requests and responses must still pass), so a breaking change fails CI rather than a phone in the shop.
- **Deploy:** `deploy.sh` builds the image, pushes it, runs `docker compose pull && up -d`, and applies the migrations (an EF migration bundle or `mealplanner migrate`, decided in M4a). GitHub Actions calls the same script later.
- **Backups:** a nightly `pg_dump` plus the photos volume, sent off the VM with **restic** (BSD licence), which encrypts everything on the VM before it leaves, so the storage provider only ever sees ciphertext. **The VM can only add to the backup repository** (restic's REST server in append-only mode, or a storage key without delete rights), and `restic forget --prune` (30 daily and 12 monthly snapshots) runs from the admin's machine, so someone who takes over the VM can't delete the backups. The restic password lives in the VM's env file and in the admin's password manager; without it the backups are unreadable, by design. A **monthly restore test** (a scheduled job) restores the latest snapshot into a throwaway Postgres container, runs a few sanity queries (families, dishes, latest change counter) and reports failure through the logs and an email to the admin.

## 7. ADRs to write

1. Blazor WebAssembly PWA over a JS framework
2. One origin, cookie auth (BFF style) over JWT
3. Offline edits limited to shopping in v1
4. IndexedDB over SQLite-in-WASM
5. Change feed with a per-family counter under a row lock
6. Family isolation through a global query filter
7. Aspire for local development, Docker Compose for deployment
8. One unit kind per grocery, amounts stored in base units (g, ml, count) over free units with a "Combine as" step
9. The live shopping list built from item sources (dish, extra, adjustment) over a frozen copy or a full recompute
10. Family id in every key and foreign key, so the database refuses cross-family links, over relying on the query filter alone
11. No step timers in v1, because a PWA can't alert reliably in the background
12. Licence policy: built-in .NET first, then MIT, Apache, BSD or the PostgreSQL License (Npgsql) only, checked before adding any package (why not FluentValidation, ImageSharp, MediatR, AutoMapper). Test-only packages that never ship may also be MPL-2.0 (axe-core for accessibility tests); CI checks the app and test projects against separate allow-lists. Also the supply-chain rules: lock files, Dependabot with a cooldown, NuGet Audit
13. snake_case database names through EFCore.NamingConventions, so SQL needs no double quotes; EF Core stays on 10.x until the package supports 11
14. Security headers and CSP sent by the app from one middleware, not by the reverse proxy, so every environment sends the same headers and SEC-05 is testable from M0

ADRs are written when their milestone starts, not all up front: M0 writes 1, 2, 7, 12, 13 and 14. The records and their status are listed in [docs/adr](../docs/adr/README.md).
