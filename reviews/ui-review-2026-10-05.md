# Family meal planner: UI review and tech choice

Reviewed: `Auth Screens (Galaxy A5)`, `Recipe Screens`, `Week Plan v3 (Galaxy A5)`, `Shopping List (Galaxy A5)`, `More Screens (Galaxy A5)`, `Family Settings (Galaxy A5)` (2026-10-05).

Note: the files are design templates. Their runtime (`support.js`, `android-frame.jsx`) wasn't uploaded, so I reviewed the structure, copy, interactions and embedded sample data, not the fully rendered look.

## 1. Is Blazor WebAssembly a good choice?

**Yes, if you're already comfortable in C#/.NET. It meets every requirement, but it isn't the lightest option.**

What works:
- The Blazor WASM template ships a PWA option (service worker, manifest, offline cache of the app shell). Install to home screen and full offline launch work on Android and desktop.
- One codebase for phone, tablet and desktop browsers.
- Put your components in a **Razor Class Library** from day one. If you later want store apps, the same components drop into **.NET MAUI Blazor Hybrid** (Android/iOS/Windows/macOS) without a rewrite.

What to plan for:
- **Startup weight on your target phone.** The Galaxy A5 is an older, low-RAM device. First load of a Blazor WASM app downloads the .NET runtime (a few MB compressed) and can take several seconds there; later launches come from cache and are fine. Keep it trimmed, use compression, and skip AOT unless profiling shows you need it (AOT makes the download bigger).
- **Offline data is your job, not Blazor's.** The service worker only caches the app. Meals, weeks and lists need local storage in IndexedDB (via a small JS-interop wrapper or a library) or SQLite-in-WASM with EF Core. Then you need a sync strategy, because two parents can edit the same week offline. Simple rule that works for this app: each record has `updatedAt`, last write wins per field, and shopping-list ticks merge (ticked anywhere = ticked).
- **iOS limits.** Safari PWAs have no install prompt (users must use Share > Add to Home Screen), limited background sync, and storage can be cleared if the app isn't used for a while. Sync to the server whenever online so nothing lives only on the phone.
- **Cook mode needs the Screen Wake Lock API** (JS interop) so the screen doesn't sleep mid-recipe.

Alternatives, for comparison: a React/Svelte/Vue PWA loads noticeably faster on old Android and has more offline-sync libraries; Flutter or React Native give true native apps. None is worth switching to unless you're not a .NET developer.

## 3. Missing screens (third pass, after "Family Settings", 2026-10-05)

Decision: no kid PINs. Everyone signs in with email and password.

**Covered by "More Screens":** navigation (4 tabs), recipe library, offline / sync failed / conflict, shopping item edit, pantry, Family tab, delete account and data, first run, start a week from last week or a template, save week as template.

**Covered by "Family Settings":** manage family (members, roles, remove, invite by email, new family code), who can do what, leave family (with owner hand-over), edit profile (incl. food I don't eat), change email, change password, notifications (incl. the iPhone home-screen note).

**Still missing:**
1. **Auth flow rework for email-only.** The Auth Screens file hasn't changed yet. Remove "Who's here?" and the PIN screen. "Join my family with a code" needs a "create your account" step (name, email, password, terms). "Create family → Your crew" should become invite by email or share the code, matching the new Manage family screen.
2. **Accepting an invite.** Manage family can now "Invite by email", but there's no screen for the person who receives it: open the link, create an account or sign in, and land in the family.
3. **Verify email after sign-up.** Change email says it uses "the same screen as sign-up", but sign-up has no verification step yet. The reset-code screen can be reused.
4. **Install prompt.** A small "Add to home screen" screen or banner, mainly for iPhone. Offline use and notifications both depend on it.
5. **Rating a cooked meal.** Permissions mention "Mark meals as cooked, and rate them afterwards", but no screen does this. Either add it (e.g. at the end of cook mode, next to "Dinner's ready!") or drop the permission.

Nice-to-have, no screen needed yet: recipe import from a link or photo.

## 4. UI notes on existing screens

- **Week grid at 360 px is tight.** Three columns leave about 95 px per cell; dish names are 10 px and clamp to 2 lines, which is hard to read for kids and for parents at arm's length. Consider a "today/day list" view (one day per row, full names) alongside the grid, or open on today.
- **Cook mode "Back" button** is dark text on a dark card and nearly invisible. Also consider showing the ingredient list (scaled) from within cook mode.
- **Add a dish:** the sticky Save button overlaps the "How to cook it" heading; add bottom padding equal to the button height.
- **Shopping list header** still has a back button (‹). Now that Shopping is a tab, drop it so the tab bar is the way out.
- **Progress "x/21"** assumes exactly 3 slots × 7 days. If a slot can be skipped on purpose (eating out), add "skip" so progress can reach 100%.
- Tap targets (40–56 px) and the warm palette look good and consistent across files.
