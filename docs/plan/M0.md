## Tasks

Task 1 is direct commits; from task 2 on, each task is one PR, merged with CI green from task 3 on. Test names start with the spec id they prove, for example `SEC_02_ordinary_request_over_64KB_is_refused_with_413`.

### 0. Spike: phone, tunnel and install (throwaway, half a day)

Only what nobody can know without trying. Task 1 doesn't depend on it and can run first.
1. **The phone.** On the Galaxy A5, record the model year, Android version and **exact Chrome version** (`chrome://version`). If it's on Android 8 or 9, Chrome 138 was the last release for it, so the family's shopping phone runs a browser that no longer gets security fixes. That version becomes the oldest supported browser, and the risk is written down in spec chapter 8.
2. **The tunnel.** An installed PWA is tied to its URL, so the tunnel must keep the same one. Try a persistent named Dev Tunnel with anonymous access; if its warning page shows inside the installed app or the URL changes, try a named Cloudflare Tunnel on a subdomain of the app's domain. Record: whether the tunnel reaches the app over HTTP or HTTPS (it matters for task 4's forwarded headers), and when an unused tunnel expires, because an expired tunnel leaves a dead home-screen icon.
3. **Install and restart.** Serve a published `blazorwasm --pwa` app through the tunnel, add it to the home screen, open it from the icon (full screen), close it, restart the tunnel, and open it again. It must be the same app with its storage intact.
4. **Speed.** On the A5, with the published app from step 3: the time from tapping the icon to a usable screen on a cold start (after restarting the phone) and on a repeat start, over Wi-Fi and over mobile data, and the download size from DevTools. These are the first numbers for chapter 8's targets, and the earliest sign of whether Blazor WebAssembly is fast enough on this phone ([ADR 1](../adr/0001-blazor-webassembly-pwa.md)).
5. **Two features later milestones rely on.** In the A5's Chrome, through remote DevTools: `'wakeLock' in navigator` (cook mode, M9) and `'share' in navigator` (sharing the list, M2b). A missing one changes that milestone's design, so it's better known now.

**Done when:** the spike app reopens full screen on the A5 through a tunnel whose URL survives restarts, or the findings change this plan; and the speed numbers and the two feature checks are recorded. Findings go under "Spike notes".

### 1. Repo bootstrap (direct commits, not a PR)

- `git init` in this folder, so `spec/` and `reviews/` are committed where they are. Done on 2026-11-10 (local commits only).
- **The pre-push review gate (D12), before the first push.** Two parts, both run by a `pre-push` hook kept in `.githooks/` (committed, so reviewers can see it):
  - **Fixed checks:** gitleaks over the commits being pushed; every commit's author and committer email must be the GitHub noreply address; no line in the diff may contain an entry from a local, untracked list of personal strings (email, phone, address, real names, the Windows user name); build and unit tests pass; commit messages follow the agreed format.
  - **AI review:** a Claude Code agent (`.claude/agents/push-reviewer.md`), run headless by the hook, reviews the outgoing commits in four separate runs: sensitive data, then as a senior developer, as an architect, and as an outside reader of the history. A FAIL needs evidence and blocks the push; what it can't check is a FLAG, shown but not blocking. Results are cached by commit content, so a re-run can't turn a FAIL into a PASS, and the author can overrule a FAIL with a binding `Review-note:` trailer. Its summary goes into the PR description; talking points for the author stay on this machine. The full checklist is [docs/review/push-review.md](../review/push-review.md).
  - The checklist and the commit-message format are agreed with the author before the gate is switched on. CI repeats the fixed checks.
- The two commits made before the gate are reworded to the commit format while still local ([push review](../review/push-review.md#before-the-first-push)).
- The GitHub repo is created, public, only after the gate works. Then: only rebase-and-merge allowed, and a ruleset on `main` (PR required, linear history, no force-push; "CI green" is added in task 3, once CI exists).
- `global.json` (D9); `Directory.Build.props` (nullable on, warnings as errors, NuGet Audit levels from D11); `Directory.Packages.props` with lock files; `nuget.config` with `minPublishAgeHours` (D11); `.gitignore`; `.editorconfig`.
- `docs/conventions.md`: vertical slices and test naming by spec id. Notes on C# 15 features are added when the first code that uses them arrives (closed hierarchies and unions in M3a and M7).
- The M0 ADRs: 1 (Blazor WASM PWA, D1, D9), 2 (one origin, cookie auth), 7 (Aspire locally, Compose in production), 12 (licences and supply chain, D3, D11), 13 (snake_case, D10), 14 (security headers in the app, D2).
- `README.md`: what the app is; prerequisites (the exact .NET SDK from `global.json`, Docker Desktop, `dotnet dev-certs https --trust`, the tunnel CLI); how to run.

**Done when:** the author agrees with the six ADRs; a test push with a planted secret, a wrong email and a personal string is blocked by the gate; and the first real push has passed it.

### 2. Solution, AppHost, database and admin commands

```
src/
  MealPlanner.AppHost/          Aspire: Postgres, Mailpit, migrate step, Server
  MealPlanner.ServiceDefaults/  OpenTelemetry, health checks, resilience
  MealPlanner.Data/             domain types, DbContext, migrations, naming setup
  MealPlanner.Server/           API, hosts the WASM files, admin commands
    Features/                   vertical slices (one so far: /api/ping)
  MealPlanner.Client/           Blazor WASM app (PWA)
  MealPlanner.UI/               Razor Class Library: components
tests/
  MealPlanner.UnitTests/        the command parser's tests, from this task
  MealPlanner.IntegrationTests/ Testcontainers Postgres + WebApplicationFactory on Kestrel
  MealPlanner.ComponentTests/   bUnit (created in task 7, with its first test)
  MealPlanner.E2ETests/         Playwright + Aspire.Hosting.Testing (created in task 8)
```
- The client starts from the .NET 11 `blazorwasm --pwa` template. Checked on 2026-11-10 with SDK 11.0.100: its `service-worker.published.js` doesn't call `skipWaiting()`, so updates already wait for Refresh as chapter 7 requires.
- Test projects use xUnit v3 on Microsoft.Testing.Platform. **A test project is created in the task that adds its first test:** the platform fails a project in which no test ran (exit code 8), and the push review's F5 and CI count any failure as a failure. So this task creates `UnitTests` and `IntegrationTests`; `ComponentTests` arrives in task 7 and `E2ETests` in task 8.
- `MealPlanner.Data` has one extension method, `UseMealPlannerDatabase(connectionString)`, that applies `UseNpgsql`, `UseSnakeCaseNamingConvention()` and `MigrationsHistoryTable("__ef_migrations_history")`.
- **One Postgres version everywhere:** one pinned image tag (major and minor) in a shared constant, used by the AppHost and by the Testcontainers fixture, and later by Compose in M4a. A data volume and an explicit dev-only password in the AppHost's `appsettings.Development.json`, so losing user secrets never locks the volume. That one key is listed in `.githooks/allowed-secrets.txt` (F6), and, if gitleaks flags it, gets a path-scoped allowlist in `.gitleaks.toml` (F1). Mailpit through the CommunityToolkit Aspire integration.
- **Admin commands:** the server executable takes a command (`mealplanner migrate`); without one it serves. The AppHost runs `migrate` as its own resource, and the server waits for it (`WaitForCompletion`). The `Initial` migration has an empty schema. `seed-demo` starts in M1a, when there's a family to seed.
- `GET /api/ping` returns the version and server time.
- `/api/*` is kept out of the WASM fallback: unknown API paths get a 404 ProblemDetails, never `index.html` with a 200.

**Tests (unit):** the command parser: `migrate` runs the migration, no command serves, and an unknown command is refused with the list of commands.

**Tests (integration, Production environment, migrated by the fixture):**
- `/api/ping` returns 200.
- `Unknown_api_path_returns_404_problem_details_not_html`.
- `Naming_convention_is_snake_case`: a test `DbContext` built with `UseMealPlannerDatabase` and a tiny entity (`TestRecord { Id, FamilyId, CreatedAt }`) creates its schema in a separate database; the test finds `test_record` with `family_id` and `created_at` in `information_schema`. It also reads the columns of `__ef_migrations_history`: if the naming convention doesn't reach EF's own history table (columns `MigrationId`, `ProductVersion`), ADR 13 records that as the one known exception.

**Done when:** Try it 1 (dashboard with Postgres, the migrate step completed, the app and Mailpit all green), and the push review's F5 has run for the first time: a push with a deliberately failing unit test is blocked, and once fixed it passes and a second push of the same tree skips the build. Also: **the lock files written on Windows restore in locked mode on Linux** (`dotnet restore --locked-mode` in the `mcr.microsoft.com/playwright/dotnet` container). The AppHost can bring in packages named after the build machine's operating system, which would make a Windows lock file fail on CI's Linux runner with NU1004; if it does, the fix is made and recorded here, before task 3 depends on it.

### 3. CI

Straight after task 2, so every later PR is checked.

GitHub Actions on every PR and on `main`:
- checkout with `fetch-depth: 0` (MinVer needs tags); `setup-dotnet` from `global.json`; restore in locked mode; build with warnings as errors; unit and integration tests (bUnit joins in task 7).
- **The push review's fixed checks again**, by running the hook's own script, `.githooks/push-review.ps1 -Ci`, over the PR's commits: secrets with gitleaks (F1), noreply emails (F2), the commit format (F4), every commit building with its unit tests passing (F5), and forbidden files and values (F6). F3 stays on the author's machine, with its list. Commits by `dependabot[bot]` get the subject check only ([conventions](../conventions.md#dependabot)).
- **Tests for the gate itself:** Pester tests (Apache-2.0) for the parsing the fixed checks rely on: the subject pattern against the cases in [conventions](../conventions.md#subject), personal strings and phone numbers, secret-looking JSON keys, trailers and the body, and which commits a push includes. And for the AI review's side, which needs no AI to test: how a reviewer's answer is checked before it's trusted, how review notes clear a FAIL, the cache key (including a commit that changes only an image), and the reason shown when a run fails, with the sensitive pass never quoting its output. A regression there would quietly weaken a check, so CI runs them on every PR.
- **licence check** with `nuget-license`: `allowed-app.json` for `src/`, `allowed-test.json` (adds MPL-2.0) for `tests/`.
- `.github/dependabot.yml` for `nuget`, `github-actions` and `dotnet-sdk` (D11), with `commit-message` prefixes `build` and `ci` and `include: scope`, so its subjects match the commit format, and `cooldown: default-days: 3` set explicitly ([ADR 12](../adr/0012-licence-and-supply-chain.md)).
- The ruleset on `main` gets "CI must be green".
- Playwright and axe join in task 8.

**Negative checks (by hand, once, on throwaway branches):**
- A realistic random-looking secret (`ghp_` plus 36 random characters, not `AKIAIOSFODNN7EXAMPLE`, which gitleaks allow-lists) fails gitleaks. This is Try it 6.
- A GPL package fails the licence check.

**Done when:** CI runs on every PR, and both negative checks have been seen failing.

### 4. Production-like run and the tunnel

- **`published` mode in the AppHost (D7):** a resource runs `dotnet publish` for the server, and a second resource runs the published output with `ASPNETCORE_ENVIRONMENT=Production`, after the migrate step. The normal `dotnet run` mode stays for day-to-day work with hot reload.
- **Forwarded headers:** `UseForwardedHeaders` for `X-Forwarded-For`, `-Proto` and `-Host`, trusting only the proxies and networks listed in a setting. Its default is loopback, which fits the tunnel client now; M4a adds the Compose network, because Caddy runs in its own container and doesn't reach the app from loopback. Without it, the app thinks every request is plain HTTP from localhost: HTTPS redirection and HSTS misbehave behind the tunnel, and in M1b rate limiting would see the whole family as one address, so one mistyped password would lock out everyone.
- **The tunnel** chosen in the spike, with its fixed URL, pointed **only at the published, Production resource**. README: one-time setup and how to open the app on the phone.

**Tests (integration):** `Forwarded_proto_from_loopback_is_trusted` (a request from loopback with `X-Forwarded-Proto: https` is seen as HTTPS, with the forwarded client address) `Forwarded_headers_from_other_addresses_are_ignored`, and `Forwarded_headers_from_a_network_in_the_setting_are_trusted`.
**Done when:** the published skeleton opens on the A5 through the tunnel, and again at the same URL after the AppHost restarts.

### 5. Guardrails: time, SQL, HTML and logs

- `TimeProvider.System` registered on the server and in the WASM client.
- `Microsoft.CodeAnalysis.BannedApiAnalyzers` on every `src/` project through `Directory.Build.props`, with one `BannedSymbols.txt`:
  - Clock: `DateTime.Now`, `DateTime.UtcNow`, `DateTime.Today`, `DateTimeOffset.Now`, `DateTimeOffset.UtcNow`.
  - Local time zone by any route: `TimeZoneInfo.Local`, `TimeProvider.GetLocalNow`, `TimeProvider.LocalTimeZone`, `DateTime.ToLocalTime`, `DateTimeOffset.ToLocalTime` (the family's zone is always explicit, DOM-24).
  - Timers that ignore `FakeTimeProvider`: `Task.Delay` without a `TimeProvider`, `new CancellationTokenSource(TimeSpan)` and `(int)`, `CancelAfter`, `new PeriodicTimer(TimeSpan)`, `System.Threading.Timer`, `System.Timers.Timer`, `Thread.Sleep`, `Stopwatch` (use `TimeProvider.CreateTimer` and `GetTimestamp`).
  - SQL: `FromSqlRaw`, `ExecuteSqlRaw`, `SqlQueryRaw` and their async forms (SEC-04, architecture §4).
  - HTML: `MarkupString` (SEC-05). Safe uses carry a suppression with a reason.
- Logging through `ILogger` and OpenTelemetry only (D8). Server tracing uses ASP.NET Core 11's built-in `Microsoft.AspNetCore` activity source.

**Negative check (by hand, once):** `DateTime.Now` in a new `src/` project fails the build, showing that `Directory.Build.props` covers new projects.
**Done when:** the negative check has been seen failing, and Try it 5 passes (the request from the laptop shows in the dashboard as one trace with its log lines).

### 6. Server hardening: SEC-02, SEC-05, SEC-09

- **Security headers middleware (D2):** CSP, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy` (camera, microphone and geolocation off), HSTS outside Development. Production policy: `default-src 'self'; script-src 'self' 'wasm-unsafe-eval' 'sha256-<import map>'; style-src 'self'; img-src 'self' data:; connect-src 'self'; object-src 'none'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`. The import-map hash is computed at startup from the `index.html` the server serves (D2).
- **CSP clean-up:** move the service worker registration into a file, then run the published app and fix every console violation.
- **Request size limit:** `MaxRequestBodySize` = 64 KB. The larger limits (256 KB for sync, 10 MB for photos) arrive with their endpoints in M2a and M10.
- **ProblemDetails:** each error gets a ref of 8 hex characters, the first 8 of its trace id (for example `4F2A91C0`), logged with the exception, so one search in the logs finds the trace. Four characters would repeat after a few hundred errors. The response is `{ title: "Something went wrong", ref: "4F2A91C0" }` with no details outside Development.
- **Bad requests keep their status:** `StatusCodeSelector` maps `BadHttpRequestException` to its own status (413, 400) with a ProblemDetails and no ref. Checked by experiment on 2026-11-10, on .NET 10.0.403 and again on .NET 11.0.0: a body over the limit reaches the app's middleware, so the 413 gets our ProblemDetails and CSP, with `Content-Length` and chunked. Oversized headers don't: Kestrel answers `431` itself, with no body and none of our headers. That's acceptable, since there's nothing for a browser to run.
- **Test-only endpoints can't reach production:** only the test fixture adds them, through an `IStartupFilter` registered in `WebApplicationFactory`. The app has no code path, environment check or setting that maps them.

**Test setup:** `WebApplicationFactory` with `UseKestrel()`, so Kestrel's limits really apply; Production environment; the fixture migrates the database and adds `POST /test/echo` and `GET /test/throw`.

**Tests (integration):**
- `SEC_02_ordinary_request_over_64KB_is_refused_with_413` (with `Content-Length` and chunked) and `SEC_02_request_under_limit_is_accepted`.
- `SEC_05_every_app_response_has_the_production_csp`: the header **equals** the Production policy (with the computed hash) on `/api/ping`, `/`, a static file, `/api/typo` (404), `/test/throw` (500) and the 413. A development-only `ws:` source or an added `'unsafe-inline'` fails it.
- `SEC_09_error_response_has_a_ref_and_no_internal_details` and `SEC_09_error_ref_is_in_the_server_log`.
- `Canary_kestrel_refuses_oversized_headers_itself`: oversized headers get a bare `431`. A canary: if it ever fails, Kestrel changed, so revisit this task's note.

**Done when:** all tests pass.

### 7. App shell, theme and About (UPD-06)

- A tab bar with four tabs (Week, Recipes, Shopping, Family) and an empty page for each. Week is `/`.
- **About lives under Family:** the Family tab (`/family`) shows an "About" row, which opens `/family/about` with a back arrow. Family stays marked active on both. M1a adds the other Family rows above About.
- `theme.css`: every colour, font, spacing and radius as a CSS custom property in one file.
- **Version and date (D4):**
  - MinVer gives `0.0.0-alpha.0.N` before the first tag; `v0.1.0` is tagged when M0 is accepted. `IncludeSourceRevisionInInformationalVersion` is set to `false`, or the SDK appends `+<commit hash>` to the version shown.
  - An MSBuild target writes the commit date (`git log -1 --format=%cI`) as `AssemblyMetadata("CommitDate", …)`.
  - **Builds without git** (Docker builds, where `.git` is excluded) take the version and date as build properties (`-p:MinVerVersionOverride=… -p:CommitDate=…`). A Release build that has neither git nor those properties **fails**, instead of showing "unknown".
  - **A `Dockerfile` for the server, built in CI on every PR** with those two properties. Nothing runs the image until M4a; building it now means the path without git is tested from the start instead of on the day of the first deploy.
  - The month is formatted with the invariant culture ("12 Sep 2026"). Checked on 2026-11-10: en-GB gives "Sept" for September.
  - **Local builds** (outside CI) add a build stamp to About ("· build 14:32:05"), so a rebuilt app on the phone can be told apart from the previous one while they share a version.

**Tests (bUnit, in the `ComponentTests` project this task creates):** the tab bar marks the active tab; the Family page links to `/family/about`; `UPD_06_about_shows_version_and_date` matches `^Version \d+\.\d+\.\d+(-[0-9A-Za-z.-]+)? · \d{1,2} [A-Z][a-z]{2} \d{4}$`, run for a date in every month, September included, and for a prerelease version.
**Screens to accept:** tab bar and empty tabs ("More Screens"), designs given during this PR (D5).
**Negative check (by hand, once):** a Release build with neither git nor the two properties fails.
**Done when:** Try it 2 and 4 on the laptop, the image builds in CI, and the negative check has been seen failing.

### 8. PWA and end-to-end tests (INST-04)

- `manifest.webmanifest`: name, short name (checked for truncation on the A5), `display: standalone`, `start_url: "/"`, theme and background colours, icons at 192 and 512 plus a maskable one.
- Splash: Android builds it from the manifest; the WASM loading screen in `index.html` matches it, so there's no flash.
- **E2E setup** (this task creates the `E2ETests` project): `Aspire.Hosting.Testing` starts the AppHost in `published` mode (D7): Postgres, migrate, and the published server in Production. Playwright for .NET at 360 px and desktop, with `Deque.AxeCore.Playwright`.
- **CSP violations fail tests:** the E2E fixture registers a `securitypolicyviolation` listener on every page and fails any test that triggers one, so an inline `style=` added in M5a is caught automatically.
- **Visual baselines (D5):** recorded and compared only in Linux, in CI or locally in the `mcr.microsoft.com/playwright/dotnet` container (a script in `tests/`). A new or changed baseline is recorded in that container and committed in the PR that changes the screen. On a failure, CI uploads the received images and diffs as artifacts.
- **Oldest browser:** a smoke test (the app loads and the four tabs open) also runs against Chrome for Testing at the version the spike found, through Playwright's `ExecutablePath`. If that Chrome is too old for the Playwright version in use, the spike notes record it and this test is dropped, so the gap is known rather than hidden.
- E2E joins CI.

**Tests (Playwright):**
- `INST_04_chrome_reports_the_app_installable`: Chrome's own check, through the DevTools protocol (`Page.getInstallabilityErrors`), returns no errors. The method is experimental, but it's Chrome's answer rather than ours. Plus: `start_url` opens Week.
