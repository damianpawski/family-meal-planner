# ADR 7: Aspire for local development, Docker Compose in production

Status: **Proposed** · 2026-11-12 · decided 2026-10-06 ([approach review §3](../../spec/approach-review.md#3-should-you-use-aspire)), detailed in the [M0 plan](../plan/M0.md) (decisions D6 and D7)

## Context

- The whole app must run locally with one command: Postgres, the server with the WebAssembly app, a fake mail inbox, and the logs and traces.
- Integration and end-to-end tests should run against the same wiring as the app, not a hand-made copy of it.
- The phone reaches the laptop through a tunnel, so a local build can be installed and tried on the Galaxy A5.
- Production is a cheap virtual machine for one family, with no lock-in to a cloud provider.

## Decision

- **Locally, an Aspire AppHost** starts Postgres, Mailpit, a migration step and the server, with the Aspire dashboard showing every log and trace (OpenTelemetry). Postgres uses one pinned image tag, shared with the Testcontainers fixture and later with Compose.
- **Migrations never run when the server starts.** `mealplanner migrate` runs as its own step before the server, and test fixtures migrate their own database. The server never changes the schema, so tests can run it in Production mode.
- **Startup order is explicit:** the migrate step waits until Postgres reports healthy (`WaitFor`), and the server waits until the migrate step has finished (`WaitForCompletion`), so a fresh start never races the database.
- **Two ways to run locally, each one command:** the normal one, with hot reload, for day-to-day work, and a `published` mode, chosen with the AppHost's `published` launch profile, that publishes the server and runs the output in Production. The phone's tunnel and the end-to-end tests use only the published mode, for two reasons: the template's caching service worker only exists in a published build, and a development server behind a public URL would show its error pages to anyone who found the URL.
- **Tests:** integration tests use Testcontainers with `WebApplicationFactory` on Kestrel; end-to-end tests start the AppHost through `Aspire.Hosting.Testing`.
- **In production, Docker Compose** on the virtual machine: Caddy (TLS with Let's Encrypt), the app's image, Postgres and Seq. Whether `compose.yaml` is hand-written or generated by Aspire, and how production migrates, is decided in M4a.

## Alternatives considered

| Option | Why not |
|---|---|
| Docker Compose for local development too | No dashboard or service discovery, and the tests would need their own wiring. |
| Installing Postgres and the rest by hand | Not repeatable on a clean machine, and different on every laptop. |
| Kubernetes, or a managed container platform | Far more to run and pay for than four users need, and tied to a provider. |
| Migrating the database when the server starts | Tests couldn't run the server as Production without changing the schema, and two copies of the app starting at once would race. |

## Consequences

- One `dotnet run` on the AppHost starts everything, with Docker Desktop as the only extra requirement.
- The AppHost and production's Compose file describe the same system twice. M4a rehearses the deploy on a local Linux machine before it's done for real.
- The published mode makes a local run slower to start, so it's used only where the difference matters: the phone and the end-to-end tests.
